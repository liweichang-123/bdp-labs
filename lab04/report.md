一、独立预测：正常提交、事务内失败、数据先提交、检查点先提交的四种状态

数据库初始已有 3 个独特事件，检查点为 3，处理新事件 X 后应推进到 4。

两项都在同一事务中成功提交：最终可见事件数 4，检查点 4，无需重放。

写入 X 后、提交前抛异常并回滚：最终可见事件数 3，检查点 3，应重放 X。

X 已单独提交、检查点尚未更新就失败：最终可见事件数 4，检查点 3，应重放 X（被 ID 去重挡掉不新增）。

检查点先提交到 4、X 尚未写入就失败：最终可见事件数 3，检查点 4，X 被永久跳过。

后两种说明两个方向都危险：进度落后可能重放，进度超前可能跳过数据；事件 ID 去重能抑制重复效果，但补不回被错误检查点跳过的记录。



二、机制：微批、事件 ID、检查点、事务与重放

微批每 500 条一个提交边界；用 event\_id 主键去重；检查点表 ID=1 记录已处理位置；事件写入与检查点推进处于同一个 SQLite 事务中，一起提交或回滚；失败后关闭连接、重开磁盘数据库、重放未提交批次。

九、必答分析题

1\. 为什么事件写入和检查点更新必须处于同一个提交边界？

答：否则失败时可能只写一半，检查点超前会导致数据被永久跳过，数据超前会在重放时产生重复效果；同一事务保证数据与进度永远一致。

2\. MAX(offset,new\_offset) 在什么顺序假设下成立？存在未完成空洞时会怎样？

答：适用于单条顺序输入序列、新 offset 永远不小于旧值；多分区并发且前面批次未完成、后面批次先完成时，取全局最大会跳过空洞中的数据。

3\. 主键去重为什么不能修复检查点已经超前但数据未写入的问题？

答：该数据从未进过数据库，主键去重没有机会看到它；检查点已跳过它，重放也到不了它。去重只能防重复，不能补丢失。

4\. 本次注入的是受控异常、进程被杀、机器断电，还是网络分区？证据支持哪一种？

答：受控 Python 异常并显式回滚。证据是 failure\_injected=true、异常信息 INJECTED\_FAILURE\_BEFORE\_COMMIT、关闭连接后重连恢复，无断电或强杀进程记录。

5\. 晚到事件为什么不等于重复事件？本章有没有 watermark？

答：晚到事件 ID 不同、发生时间更早但最后到达，是合法新事件；重复事件是同一 ID 再次投递。本章没有 watermark，只做全历史汇总，不涉及窗口关闭。

6\. 本章的事务性效果限制在哪个系统范围内？为什么不能写 Kafka exactly-once 已实现？

答：限制在单个 SQLite 数据库内的事件写入与检查点事务性；本章未接 Kafka、未跨系统或跨机器，不能使用全局 exactly-once 的表述。
