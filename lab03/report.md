二、独立手算预测



预测一（分区与哈希）：假设 12 条数据，A 占 8 条、B 占 3 条、C 占 1 条，哈希取模分到 4 个区，则四个区的数据量分别为 8、3、1、0 条。如果增加到 8 个分区，由于只有 3 个不同键，仍然只有 3 个非空分区，无法自然产生 8 个均匀分区。

预测二（加权平均）：全局平均延迟应使用总延迟除以总记录数，即 (2×10 + 8×100) / 10 = 82 毫秒，不能直接取 (10+100)/2 = 55 毫秒，因为两个分区的样本量不同，必须考虑加权分母。



三、执行结构与正确性



Dask 在本机使用 LocalCluster 启动多个 Worker 进程，通过进程 ID 证明是真实多进程执行。程序读取 Silver Parquet 后按 service 字段进行 Shuffle 重新分区，再分组聚合，最后用 DuckDB 进行 SQL 参照计算。三次运行的 matches\_duckdb 均为 true，说明 Dask 与 SQL 的聚合结果完全一致。

两次双 Worker 配置的运行中，worker\_pids 分别包含了两个不同的进程 ID：w2p8 为 11132 和 16296，w2p4 为 6964 和 13396，证明是真实的双进程执行。

五、倾斜分析



按 service 字段 Shuffle 后，8 个分区中只有 3 个非空，行数分别为 2023、14008、3969，最大的 assistant 服务占据了 14008 条，热键明显。分区数 8 不等于 8 台机器，也不等于 8 个 Worker；本实验 Worker 数由 n\_workers 决定，而分区数是计算组织单元。增加分区数不能把单个热键自动拆成多份。



六、独立改动：慢请求统计与错误率扩展



慢请求阈值从 1000 修改为 2000，慢请求率从 75% 左右降至约 50%，总请求数和总延迟不变。

随后在附件现有 main() 中补全了 errors 和 error\_rate 的聚合：Dask 路径新增 is\_error 标志并按服务聚合；DuckDB 路径新增 CASE WHEN status='error' 的计数；结果字段重命名为 errors；最后计算 error\_rate = errors / requests。该实现通过了独立核验器 check\_error\_extension.py --threshold 2000，输出 ERROR\_EXTENSION\_PASS，其中 total\_errors 为 800。

八、失败恢复与结论局限



非法配置 workers=0 被正确拒绝，报错为 ValueError: Teaching limits: 1-4 workers, 1-64 partitions，说明配置边界检查有效；随后恢复为 workers=2，运行成功。

本章证明了多进程计算的正确性与 SQL 结果一致、分区倾斜对性能的影响、以及自定义错误率统计的有效性；但未验证跨机器容灾、弹性伸缩和真实生产集群的性能。结论不能超出本机实验的边界。



九、分析题



1\. 8 个分区不等于 8 台机器或 8 个 Worker？答：分区是数据块的逻辑划分，Worker 是实际执行任务的进程，本机可以只有 2 个 Worker 却划分 8 个数据块。

2\. 3 个服务键经 Shuffle 后很难均匀填满 8 个分区？答：显式按 service 哈希分配时，只有 3 个键就意味着最多只有 3 个非空分区，其余分区必然为空。

3\. 不能对不同大小分区的平均值直接取平均？答：平均值的分母是记录数，不同分区记录数不同，必须用加权平均，否则小样本分区会被高估。

4\. total\_seconds 为什么包含超过主计算的工作？答：除了主聚合之外，程序还额外执行了分区行数诊断，这部分时间也计入总耗时。

5\. 两 Worker 比一 Worker 慢时应检查什么？答：检查启动开销、数据规模、序列化成本、分区倾斜、调度开销，以及是否受磁盘和内存瓶颈影响。

6\. 本机多进程为什么不足以证明生产跨机容错？答：所有进程都在本机回环地址上运行，没有真正的网络断开、节点故障和跨机数据交换，不能模拟生产集群的容灾行为。
